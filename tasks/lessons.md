# 教訓

このリポジトリで受けた修正と、同じ失敗を繰り返さないためのルール。

## シェル設定は起動経路を両方試してから完了と言う

**2026-09-12 / 指摘: 「他のディレクトリで cc が使えなくなった」**

`~/.local/bin`（`claude` の実体がある場所）を PATH に足す処理を `.zprofile` にだけ書いた。
`.zprofile` はログインシェルしか読まないため、非ログインの対話シェル（別シェルから起動した
`zsh`、エディタの統合ターミナルなど）では `claude` が見つからず、`cc` エイリアスが
`command not found` になった。

検証時に `zsh -lic`（ログイン）だけを試して「クリーンなログインシェルで解決する」と
報告したのが原因。起動経路という別の軸を潰していなかった。

**ルール**

- zsh の設定を変えたら、必ず `zsh -lic` と `zsh -ic` の両方で確認する
- PATH は `zsh/path.zsh` に集約し、`.zprofile` と `.zshrc` の両方から読ませる。
  二重読み込みで重複しないよう冪等に書く
- 「クリーンな環境で動いた」は 1 パターンを潰しただけ。同じ機能に複数の起動経路が
  あるなら、全部の経路を列挙してから検証する
- 検証で潰した穴は `doctor.sh` に検査として残す。次に踏まないようにする

## 変更前の挙動と比べてから原因を断定する

同じ指摘のとき、まず変更前のコミットの設定を一時 HOME に展開して再現を取った。
結果、この穴は変更前から存在していた（親プロセスから PATH を継承していたため
表面化していなかっただけ）と分かり、「自分が壊した」という誤った説明を避けられた。

**ルール**: 「〜できなくなった」と言われたら、直前の変更を疑う前に変更前の状態で
再現するかを確かめる。git があるので数分でできる。

## 「どの端末から使うか」を確かめる前に完了と言わない

**2026-09-12 / 指摘: 「ghostty では使えました。でも私は orca を使用していて、orca ではうまく動きません」**

`brew` が cwd を読めずに落ちる問題を `zsh/path.zsh` で直し（`eval "$(cd / && "$__brew" shellenv)"`）、
`zsh -lic` / `zsh -ic` の両経路とクリーンな環境変数で検証して完了と報告した。修正自体は正しかったが、
ユーザーが日常的に使っているのは ghostty ではなく Orca で、そちらには別の原因が残っていた。

真の原因は macOS の TCC。Orca はターミナルを `/usr/bin/login -flpq …` 経由で起動するため、
生まれた zsh は Orca.app の TCC 権限を継承できず、`~/Desktop` 配下が丸ごと
`Operation not permitted` になっていた。`brew` は起動時に cwd の可読性を検査するので、
数ある症状のうち最初に目立っただけだった。Orca のデーモン（アプリ再起動後も生き残る）を
終了してから起動し直すと解消した。

**ルール**

- 環境依存の不具合は、シェルの起動経路だけでなく **どのアプリがそのシェルを起動しているか** も軸になる。
  直す前に「普段どこから使っているか」を確認する
- 自分がどの配下で動いているかは親プロセスを遡れば分かる。`ps -o pid,ppid,comm -p <pid>` を
  ppid が 1 になるまで辿る。これを最初にやれば、ghostty で検証しても意味がないと気づけた
- Orca が絡む調査では `orca terminal create --command … / terminal read` で実環境の出力を直接取れる。
  推測で切り分けず、ユーザーの環境そのもので測る
- ユーザーのプロセスを落とす操作（デーモンの kill など）は、自分がその配下にいないか確認してから。
  配下にいるなら自分で実行せず、外のターミナルで実行する手順を渡す
- `~/Desktop` `~/Documents` `~/Downloads` は macOS が特別扱いする。ここを作業場所にすると
  アプリごとの権限差で不可解な失敗が出る。開発用のディレクトリはこの 3 つの外に置く
