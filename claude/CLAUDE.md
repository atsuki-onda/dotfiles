# 言語

- 返答、コミットメッセージ、PRの説明は日本語で書く
- コード内の識別子とコメントは既存コードの言語に合わせる

# 作業ルール

- タスクと無関係なコードは変更しない
- 破壊的な操作（force push、rm -rf、DB変更）は実行前に確認する
- 複数ファイルに渡る変更は、実装前に方針を短く提示する

# ワークフローの進め方

## 1. プランモードを基本にする

- 自明でないタスク（3ステップ以上、またはアーキテクチャ上の判断を含むもの）では必ずプランモードに入る
- 想定外の事態になったら即座に止まって再計画する。無理に押し進めない
- 構築時だけでなく検証ステップにもプランモードを使う
- 曖昧さを減らすため、事前に詳細な仕様を書く

## 2. サブエージェントの活用方針

- メインのコンテキストウィンドウをきれいに保つため、サブエージェントを積極的に使う
- 調査、探索、並列分析はサブエージェントに任せる
- 複雑な問題では、サブエージェントを通じてより多くの計算資源を投入する
- 1つのサブエージェントには1つの方針だけを割り当て、集中して実行させる

## 3. 自己改善ループ

- ユーザーから修正を受けたら、必ず `tasks/lessons.md` にそのパターンを記録する
- 同じ間違いを防ぐためのルールを自分自身に向けて書く
- 間違いの発生率が下がるまで、この教訓を徹底的に改善し続ける
- セッション開始時に、該当プロジェクトの教訓を見直す

## 4. 完了前の検証

- 動作することを証明せずにタスクを完了扱いにしない
- 必要に応じて main と自分の変更の挙動を比較する
- 「スタッフエンジニアならこれを承認するか?」と自問する
- テストを実行し、ログを確認し、正しさを実証する

## 5. エレガントさを求める（バランスを保って）

- 自明でない変更では、一度立ち止まって「もっとエレガントな方法はないか?」と問う
- 修正がハック的に感じたら、「今知っていることをすべて踏まえて、エレガントな解決策を実装する」
- 単純で明白な修正ではこれを省く。過剰設計しない
- 提示する前に自分の成果物を自ら批判的に見直す

## 6. 自律的なバグ修正

- バグ報告を受けたら、そのまま修正する。手取り足取りの指示を求めない
- ログ、エラー、失敗しているテストを特定し、それらを解決する
- ユーザー側のコンテキストスイッチをゼロにする
- CI で失敗しているテストは、やり方を指示されなくても修正しに行く

# タスク管理

1. **まず計画する**: チェック可能な項目として `tasks/todo.md` に計画を書く
2. **計画を確認する**: 実装を始める前に確認を取る
3. **進捗を追跡する**: 進めながら項目を完了にしていく
4. **変更を説明する**: 各ステップで概要レベルのまとめを示す
5. **結果を記録する**: `tasks/todo.md` にレビューセクションを追加する
6. **教訓を残す**: 修正を受けたら `tasks/lessons.md` を更新する

# 基本原則

- **シンプルさを最優先**: すべての変更を可能な限りシンプルにする。影響するコードを最小限にする
- **怠けない**: 根本原因を突き止める。一時的な修正はしない。シニア開発者の基準を守る
- **影響を最小限に**: 変更は必要な箇所だけに触れる。バグの混入を避ける
